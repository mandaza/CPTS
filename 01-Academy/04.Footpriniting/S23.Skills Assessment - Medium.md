## Footprinting Skills Assessment — Medium (Windows file server)

Goal: obtain the credentials of user **HTB**. "Server everyone on the internal network has access to" → file server.

## Attack chain
1. **Full port scan** (`-Pn`, ping blocked) → 111/rpcbind, 135, 139, 445, 2049/NFS, 3389/RDP, 5985/WinRM. Host = `WINMEDIUM`.
2. **NFS** — `showmount -e` reveals export `/TechSupport (everyone)`.
3. **Mount + read** — files owned by nobody(65534), mode 700. Read as **root** (or `sudo -u '#65534'`). One non-empty file: a support ticket.
4. **Ticket** leaks `alex:lol123!mD` (an SMTP config).
5. **RDP in as alex** (alex is a normal user, NOT a local admin).
6. On the box, a **second credential** `sa:<sa-pass>` is stored in a dev/share location.
7. **Run SSMS as administrator**, use the sa password at the UAC prompt (reused as the Administrator password) → connect to local MSSQL.
8. **Query the DB** → read the HTB user's row.

## Commands I actually ran
```bash
# 1. ports (ping blocked)
nmap -Pn -p- --min-rate 2000 <TARGET>
nmap -Pn -sV -p111,135,139,445,2049,3389,5985 <TARGET>

# 2. NFS
showmount -e <TARGET>                                    # /TechSupport (everyone)
sudo mount -t nfs <TARGET>:/TechSupport /mnt/techsupport -o nolock
sudo ls -laR /mnt/techsupport                            # read as root (files = nobody:700)
sudo grep -rl . /mnt/techsupport                         # find the one non-empty ticket -> alex creds

# 3. RDP as alex (v2 xfreerdp more reliable than xfreerdp3 here)
xfreerdp /v:<TARGET> /u:alex /p:'<alex-pass>' /cert:ignore /dynamic-resolution
```
In the RDP session:
```
# find the second cred (sa:<sa-pass>) in the dev share on the box
# right-click SSMS -> Run as administrator -> enter the sa password (reused for Administrator)
# SSMS connects to the LOCAL MSSQL (1433 is localhost-only, that's why it's closed externally)
```
```sql
SELECT * FROM accounts.dbo.devsacc;   -- the HTB user's row -> username + password
```

## Notes to self
- **Why SSMS failed as plain alex / sa:alex-pass:** alex isn't a local admin and the sa password is a *different* cred found on the box. MSSQL grants sysadmin to `BUILTIN\Administrators`, so you need the elevated (Run-as-admin) token to connect via Windows auth — or the real `sa` password via SQL auth.
- **MSSQL was localhost-only** (1433 closed externally) → the DB can only be read from an interactive RDP+SSMS session. No headless/WinRM route since alex isn't in Remote Management Users.
- Password reuse again: the `sa` password doubled as the Windows **Administrator** password.
- `Edit Top 200 Rows` (GUI) or a plain `SELECT *` both read the table; the target table was `accounts.dbo.devsacc`.
- xfreerdp v2 (`xfreerdp`) activated reliably where **xfreerdp3** kept hitting `ERRCONNECT_ACTIVATION_TIMEOUT`.

## Gotchas / troubleshooting (what actually slowed us down)
- **NFS perms:** the share mounts but the dir is `nobody:nobody 700`. My normal user (uid 1000) = permission denied. Reading worked as **root** (no_root_squash on this export) via `sudo`; `sudo -u '#65534'` was denied. Key file-finder: only `ticket...782.txt` had a non-zero size among hundreds of empty tickets.
- **sudo in this setup:** Claude's shell can't prompt for sudo, and the `!` prompt in Claude Code is also non-interactive → run `sudo` mounts/reads in a **separate real terminal**. (sudo wants the *login* password, not a separate "root" password.)
- **Wrong tracks that failed:** `Administrator:alex-pass` (WinRM clean fail), `sa:alex-pass` (SQL login failed), plain (non-elevated) SSMS as alex (login failed for `WINMEDIUM\alex`). The real `sa`/Administrator password was a separate credential found on the box.
- **RDP flakiness:** connection hung ~80 min once then `ACTIVATION_TIMEOUT` = HTB **VPN drop**, not a flag issue. Verify the box is up first (`nmap -Pn -p3389 <ip>`) before blaming the command.
- **Box respawn:** the target IP changed mid-session (reset) → the old NFS mount goes stale; re-check the new IP and re-mount if needed. Creds carry over.
- The two walkthrough screenshots the user shared confirmed the path (SSMS → Run as administrator → UAC wants `WINMEDIUM\Administrator`); the `sa` password came from a lab writeup after `sa:alex-pass` failed.
