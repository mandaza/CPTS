- Usually, the initial access to a remote server is on a low-privileged user, which would not give us complete access over the box. 
- To gain full access, we will need to fin an internal/local vulnerability that would escalate our privileges to the `root` user on `Linux` or the `administrator/SYSTEM` user on `Windows`.

#### Scheduled Tasks
- There are usually two ways to take advantage of scheduled tasks (Windows) or cron jobs (Linux) to escalate our privileges:
	1. Add new scheduled tasks/cron jobs
	2. Trick them into executing malicious software
- To add new cron jobs, we need write permissions in these directories:
	1. `/etc/crontab`
	2. `/etc/cron.d`
	3. `/var/spool/cron/crontabs/root`
- We can write a bash script with a reverse shell command that will send a reverse shell when executed.

#### SSH Keys

- If we have read access over the `.ssh` directory for a specific user, we may read their private ssh keys found in `/home/user/.ssh/id_rsa` or `/root/.ssh/id_rsa`, and use it to log in to the server.
- If we can read the `/root/.ssh/` directory and can read the `id_rsa` file, we can copy it to our machine and use the `-i` flag to log in with it:

![[Pasted image 20261103164403.png]]


`NB: Note that we used the command 'chmod 600 id_rsa' on the key after we created it on our machine to change the file's permissions to be more restrictive. If ssh keys have lax permissions, i.e., maybe read by other people, the ssh server would prevent them from working.`

- If we find ourselves with write access to a users`/.ssh/` directory, we can place our public key in the user's ssh directory at `/home/user/.ssh/authorized_keys`.
- This technique is usually used to gain ssh access after gaining a shell as that user. The current SSH configuration will not accept keys written by other users, so it will only work if we have already gained control over that user.
